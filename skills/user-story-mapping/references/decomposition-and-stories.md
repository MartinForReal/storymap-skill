# Decomposition into tasks and per-persona stories (Step 2)

Decompose each backbone activity into the user's smaller steps (tasks), then write deliverable per-persona stories under those tasks — and when there are **≥3 personas, run the generation as a parallel `Agent` sweep**, one subagent per persona, then merge and dedupe. This is the loop's generate/update stage, and it owns the move from "here is the backbone" to "here is every story, attributed to whose journey it serves."

## When to use

This is Step 2 of the loop: after the backbone is set (Step 1) and before slicing (Step 3). On a non-empty baseline (an iteration) it still runs, but it carries prior tasks/stories forward instead of inventing from zero — see [On a non-empty baseline](#on-a-non-empty-baseline) below.

## Tasks and stories

- **Tasks** = the user's smaller steps within an activity.
- **Stories** = deliverable increments under tasks. Standard form: **As a/an `<persona>`, I want to `<action>`, so that `<outcome>`**. Skip the form when it would be noise.
- If a task has **>7 stories**, it's probably two tasks — split it.
- **Stories are a blueprint, not the final spec.** The form intentionally underspecifies — it captures *intent*, not *behavior*. Behavior gets pinned down later, at Step 4a (Gherkin acceptance criteria) and Step 4b (E2E contract). If you find yourself writing implementation detail in a story ("click a React button that calls `/api/v1/refunds` with an idempotency key…"), stop — that belongs in the ACs, not the story.

Each story bullet, when emitted to `storymap.md`, carries `[slice:<id>]` (required) and optionally `[persona:<name>]` and `[status:<state> | <evidence>]`. The story IDs in the derived `storymap.csv` are `S001`…, assigned in document order and regenerated by the parser — never hand-assigned here.

## Per-persona coverage is mandatory

Every persona named in `design.md` must appear as the `<persona>` of **at least one slice-1 story**. This is the slice-1 governing rule (Rule 2) stated in [../SKILL.md#rules-that-govern-every-run](../SKILL.md#rules-that-govern-every-run); the how/why and the violation cases are owned by [slicing-strategies.md](slicing-strategies.md#the-slice-1-rule--mechanics-why-and-violations). What Step 2 contributes is the *raw material* — without per-persona stories, slice 1 silently optimizes for the loudest persona and the others' journeys never ship.

- A single backbone activity often produces multiple stories with different personas (e.g. "Sign in" → admin SSO setup, end-user sign-in, compliance role-claim verification).
- Stories with no persona (pure infra / cron) live in the cross-cutting section and **do not** count toward coverage.
- If a persona has **zero** slice-1 candidates, that is a signal — **never** a silent drop; the remediation (re-slice vs. re-derive that persona's stories) is owned by [slicing-strategies.md](slicing-strategies.md#the-slice-1-rule--mechanics-why-and-violations).

## Parallelize via the `Agent` tool when persona count ≥3

Spawn **one subagent per persona**. Each receives:

- the backbone,
- that persona's verbatim quotes / pain points / constraints,
- **the full persona roster** (so it can spot cross-persona handoffs — see below),
- the story-form template, and
- an "in-character" instruction.

Run them in parallel — one message, multiple `Agent` calls. Then **merge, dedupe, and flag conflicts**: the same activity surfaced by multiple personas is often one story seen from different angles — keep the most user-voiced framing, fold the rest in, and mark genuine conflicts for the user rather than silently picking a winner. For **≤2 personas**, inline generation is fine; the sweep isn't worth the overhead.

When you write stories, attribute each to its source per the priority order in [../SKILL.md#rules-that-govern-every-run](../SKILL.md#rules-that-govern-every-run) — a real user quote outranks a simulated persona's invention, and the source tag on the bullet records which it was.

## Refine the cross-persona interaction map

The `## Persona interactions` map is **first built at Step 0.3** (the pre-interview simulation) using anticipated activities. Step 2 **refines** it against the now-real backbone: bind each interaction to the actual activity it occurs at, and where one persona's story is a precondition for another's, finalize the cross-persona `H:` `depends_on` edge. Because each per-persona subagent here already holds the full roster, it surfaces any handoff the simulation missed — fold those in.

The full protocol — the interaction-map table, how a handoff becomes a cross-persona `depends_on` edge, conflict routing, and the resulting slice-1 feasibility risk — is owned by [persona-simulation-and-gap-filling.md](persona-simulation-and-gap-filling.md) (its protocol Step 4 — Aggregate: the persona interaction map). Don't re-derive the handoff → depends_on → risk chain here; refine the activity bindings and link.

## On a non-empty baseline

When the loop runs over an existing codebase or tracker (an iteration), existing routes / components / handlers / endpoints are **pre-existing task candidates** under their activity — reuse the team's existing naming, and reuse the tracker's existing epics / components / labels read-only rather than inventing parallel ones (the taxonomy-reuse rule is owned by [work-item-tracking.md](work-item-tracking.md#align-to-the-existing-tracker-taxonomy)). Prior task/story IDs carry forward; new items get fresh IDs from `max(prior_id) + 1` — never renumber.

## Anti-patterns

- **Generating 80+ stories then running out of turns.** The most common failure mode. Cap proactively (≤50 total, slice-1 ≤15).
- **Writing implementation detail into stories.** That is Step 4a/4b territory; a story that names an endpoint or a button is over-specified.
- **Skipping the parallel sweep at ≥3 personas** and hand-rolling every persona's stories serially — slow, and it biases toward whichever persona you wrote first.
- **Silently dropping a persona with no slice-1 candidate** instead of re-running Step 3 or Step 1.
- **Inventing a new tracker epic/component** on an iteration when an existing one fits — drift, not reuse.

## Cost ceiling

Step 2 should consume **15-20%** of the run budget. With ≥3 personas the parallel sweep is the bulk of it; cap stories proactively (≤50 total, slice-1 ≤15) — generating 80+ stories and then running out of turns is the dominant way this step fails.
