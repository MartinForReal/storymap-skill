# Storymap and adjacent planning skills

**Keep Storymap in charge of the release cut, not the implementation plan.** Its distinctive question is: what is the smallest demoable release that connects the whole active journey and serves every named persona? The neighboring tools own premise challenge, design approval, technical decomposition, or execution state. The most useful adaptation is to reuse upstream decisions and reopen only a material gap exposed by the map.

Source snapshot: November 25, 2026. Storymap baseline: [`origin/main` at `35cf8a10`](https://github.com/MartinForReal/storymap-skill/tree/35cf8a10fc240f809eb7c248c8f3a254e856c65f). This compares checked-in instructions, not execution tests, installed releases, or automatic trigger behavior.

## What to borrow and where to draw the line

These are **recommendations**, not claims that upstream automatically consumes Storymap output. Read the [baseline integration reference](https://github.com/MartinForReal/storymap-skill/blob/35cf8a10fc240f809eb7c248c8f3a254e856c65f/skills/user-story-mapping/references/framework-integration.md) as proposed handoff guidance, not as an invocation protocol.

1. **Superpowers: make the handoff explicit.** The pinned brainstorming hard gate says to invoke `writing-plans` next after approval and no other skill. Don't insert a mandatory hook there. Run Storymap as a separate user-requested shaping step; give its approved cut as additional input to a user-directed plan or update. Link the actual `*-design.md`, not a guessed `design.md`. Send accepted constraints, selected stories and acceptance proof, not a rule that every story becomes a 2–5 minute task. Exact files, interfaces and execution approval stay downstream. [Brainstorming gate][sp-brain] · [Task right-sizing][sp-plan]
2. **gstack: discovery first when the premise is open.** Mapping a raw `/office-hours` ask first can harden an untested premise. Map from the approved design; don't mistake the discovery memo or root `DESIGN.md` (design system) for that brief. For review, send why/non-goals to CEO, handoffs and unproven behavior to engineering, and relevant persona friction to design/DX. `/autoplan` owns its active plan and approval procedure. The map is evidence, not that plan. `/plan-devex-review` investigates developer onboarding and friction rather than general backlog ranking. [Design/memo handoff][gs-handoff] · [Design finder][gs-finder] · [DevEx][gs-dx] · [Autoplan][gs-auto]
3. **GSD: translate outcomes and risk, not cardinality.** Local examples use `.gsd/Brief.md`, `.gsd/Roadmap.md` and a fixed first milestone sketch. Pinned GSD Pi uses `.gsd/PROJECT.md`, `.gsd/REQUIREMENTS.md` and scoped `.gsd/milestones/<id>/<id>-CONTEXT.md` / `<id>-ROADMAP.md` with DB-backed tools. Treat commands and paths as version-dependent. A Storymap release cut can inform a milestone; it doesn't prescribe a GSD slice per activity or task per story. A refund request, operator approval and customer notification might form one risk-first GSD capability proving the money-movement boundary. Pass outcome, handoffs, risk and demo evidence; leave decomposition, IDs and state writes to GSD. [Commands][pi-commands] · [Discussion][pi-discuss] · [Milestone proof and state rules][pi-plan]
4. **Spec Kit: borrow traceability, not the pipeline.** A P1 journey is independently demonstrable; Storymap slice 1 covers all active activities and personas *together*. Don't equate `P1` with `slice:1`. Borrow `/analyze`'s read-only consistency check inside the existing handoff: flag an approved outcome with no story, a missing activity/persona, or an uncovered boundary in the E2E contract if requested. Link the source and gap rather than creating new spec/plan/tasks files or another review stage. [Spec][sk-spec] · [Analyze][sk-analyze] · [Coverage rule](../skills/user-story-mapping/SKILL.md#rules-that-govern-every-run)

## Smallest useful change

- **Intake:** name the actual upstream source and whether the user approved it. Reuse approved outcomes, constraints and non-goals. Use the existing fast confirmation when there's no material delta; if blocked, ask the highest-impact unresolved question and say what the answer changes. Drafts, review findings and simulated personas are not approval.
- **Handoff:** link the source, selected cut and demo/acceptance evidence. Name the open scope decision and its owner; say what the downstream planner may decompose without reopening scope. Link the ranked tracker view when applicable instead of promising `backlog.md`. Leave the canonical map sufficient when no downstream tool was named.
- **Two proposed checks:** an approved brief with no scope delta should yield a quick confirmation and a handoff to the actual brief, not a second discovery process. A tracked refund flow with an unapproved policy change should surface the decision without folding it into slice 1, preserve the prior map and tracker keys, and honor tracker-gated output.

These changes need no new artifact schema, framework state writes, auto-chaining, parallel approval ledger or relaxation of existing coverage and tool caps.
